# What adding a source costs

An audit for decision 0049, taken on main at `81aafecb` (2026-11-03) and still true at `de9f10c6`. It lists every place outside a connector's own package that a new source must touch today, says whether each is the source's own code or a list a declaration could feed, and sets the target.

**Now: 41 files outside the connector's package, 36 to edit and 5 to add, in 8 packages and `scripts/`. When one is missed, the compiler catches 2 of them.**
**Target: one entry in `packages/sources`, and for a writable connector one more line in `packages/changeset/src/writers.ts`. A test catches a missed one.**

Both counts leave out what is the connector's own in any design: its fixture in `fixtures/<kind>/`, its eval cases, its decision and its lines in SPEC §4, §5 and §8.

## How it was counted

- Every non-test file outside `packages/slack` that names Slack: 24 source files, 22 of them in code rather than comments, plus a migration, 4 `package.json` files, 4 scripts and 10 eval cases and climbs. 25 source files name the folder outside `packages/folder`, and 55 name Jira outside `packages/jira`.
- Slack's two PRs, `git log --stat`: OA-23 (#46, reading) changed 26 files outside `packages/slack` and `fixtures/`, 20 of them not tests or cassettes; OA-28 (#74, writing) changed 21.
- A compile probe: a fourth kind, `sheets`, added to core's `sourceKinds` with a key shape. `pnpm typecheck` then fails in 2 files, the list in `packages/sources` and the eval module-size test. Everything else compiles, and fails at run time or quietly does the wrong thing.

Much already derives from the declaration, since OA-79, OA-61 and OA-134: the item docs, namespaces, op specs, panels, facets, recognizers and overview candidates. So do the source names in `server/src/dropped.ts` and the sidebar's source rows, and `check-repo.ts` builds its writer rule from `sourceKinds`. What is left is how a source is connected, kept, run and shown.

## The target

A new connector is one package, `packages/<kind>`, that declares itself once, and one entry in `packages/sources`. Everything else derives from the declaration:

- **its ID kind:** `kind` and `key`; core keeps no list of kinds;
- **its secret names:** none of its own; the server names each connection's secret `connection.<ULID>`;
- **its Settings section:** its declared options, drawn one way under Connections;
- **its first-run step:** its declared connect steps, drawn by the same component;
- **its writer registration:** one line in `packages/changeset/src/writers.ts`, the one file that builds writers. The declaration can't name its writer, because everything that imports the declarations would then have an import path to a `SourceWriter` (decision 0003). A test compares that list with the declarations that have op specs.

Hand-written, in the package, as today: sync, the mapping from a source's records to items, the writer, the panel's view, the recognizer, the overview's candidates, and the server half of each connect step.

## The probe, and what it proves

The riskiest part of the seam is taking the list of kinds out of core: core, db, bindings and changeset all iterate `sourceKinds`, and bindings builds the agent's namespace names from it. The probe made core generic (`SourceKind` any string, one universal key shape) and ran `pnpm typecheck`, then reverted:

- 44 errors in 15 non-test files, and 27 in tests;
- of three kinds only: `sourceKinds` no longer exported (11 files); parameters implicitly `any` because of it; and types that leaned on the closed list, "possibly undefined" where a `Record<SourceKind, …>` had been exhaustive, and two mapped types;
- in db (2 files), bindings (2), changeset (1), server (6), sources (1), groupings (1), evals (1) and `check-repo.ts`.

The probe leaves out what 0049's numbered prefix adds (`jira.2:ACME-4`). Every stored `source` column, each source's sync state and the writers are keyed by the prefix. `parseItemId`'s `source` gives way to a kind and a prefix, so the compiler lists every caller that builds an identity, such as the change-set store's stable-ID lookup, workstream members and the sync worker. The places that cut an ID's prefix by hand don't go through it and move onto it: `web/src/chip.ts`, `web/src/block.tsx`, `web/src/window-page.tsx`, the change sets' SQL in `db/src/threads.ts`, the index's prefix pattern in `db/src/index-store.ts`, `server/src/dropped.ts`, `bindings/src/fn.ts`, `server/src/scripted-agent.ts`, the eval harness's `case.ts`, `runner.ts` and `shown.ts`, and each connector's own ID type in its `.d.ts`, such as Jira's `JiraId`.

It proves the move is mechanical: packages below `packages/sources` can take kinds as data, from the namespaces, item docs and op specs they are already given, and exhaustiveness comes back from the declarations list. It doesn't prove that one component can draw every connector's connect steps as well as OA-191's hand-made Jira rows; decision 0049 maps each connector's steps onto the step kinds, and the Connections story measures the first run against its budget.

## Ideas, interface not settled

Three ways a person might shape a connector for themselves. None is decided or planned: the maintainer wants to work out their interface first.

1. **Notes for a connection:** what the person writes about a source, such as "RAG means red, amber, green; Blocked means waiting on legal".
2. **Saved asks:** questions to ask again in one click, for a connection or a workstream.
3. **Recipes:** named scripts over the bindings, run in the sandbox, whose writes come out as change sets.

Open questions:

- **Where it reaches the agent:** in tool results, as source content must (CLAUDE.md), so it costs nothing on turns that don't read that source, or somewhere a recipe could be named in the module?
- **Where a person writes and finds them:** on the connection in Settings, in the item panel, in the thread where it came up, or a page of its own?
- **How the agent drafts one:** after it learns something in a thread ("Remember that RAG is health, not progress?"); whether it is held for the person as decision 0051's drafts are; and how the person reads the full text before keeping it.
- **Sharing and trust:** text or a script from someone else is untrusted until the person reads and approves it, and a recipe is code most people can't read. Can a recipe shared by a teammate be trusted, and should the agent be able to call one?
- **How they show in Settings and the window:** which notes the agent had in a turn, which saved asks a workstream offers, and what happens to all three when a sheet's columns change under them.
- **How they're tested:** an eval can check that a person's text arrives where it should, but can't grade the text itself.
