# 0038 The first run sets up the person's AI and their first source, with no terminal

Accepted 2026-11-03 (OA-190, OA-191). Amends 0020, 0022, 0036 and 0037, and follows 0040. Changes SPEC §4, §5 and §7, and the security reviewer's checklist. Amended by 0044: which Claude Code the check guards, and how; a cluster the window chat can make a workstream of; when the first run's overview ends; Jira's project list in the window too. Amended by 0049: the source step's rows are drawn from each connector's declaration. Amended by 0051: Google Sheets' row adds the mapping the agent drafts.

Adds: none

**Decision.**

- **Nobody sees a terminal.** When the person's command-line agent (the CLI) is missing or signed out, Oriel runs its vendor's own installer and the CLI's own sign-in for them, as children of the server, and says what is happening in plain steps. When something fails, the row says what is known in one sentence, never more than it knows (an install that stopped "didn't finish"; it doesn't promise nothing changed), with Try again and Show details: the run's log, which the person can copy to whoever helps them. The log never holds a password, a key, a code, an email, or the sign-in link's query.
- **What Oriel runs** is a fixed list, with every argument in code, never a string from the page. The page asks for an action by name (check, install, sign in, update, cancel), behind the launch secret (0036). It is for Claude Code alone: the harness runs on nothing else (0037, 0040).
  - **Install:** the vendor's installer script, from a URL fixed in code (`https://claude.ai/install.sh`), fetched over HTTPS, saved in a folder only the person can open, and run unmodified by `/bin/bash`. Never with sudo. Its environment is the harness's allowlist (0037) with a fixed system PATH, `/usr/bin:/bin:/usr/sbin:/sbin`, in place of the person's, so nothing planted on their PATH runs in its place. Oriel installs a version the harness supports: when the vendor's latest is outside the harness's range, it names the newest supported version, which the installer takes as an argument. The row shows the installer's phases (downloading, setting up, checking it's genuine) and the time so far, since the installer reports none.
  - **Whom the install trusts.** The vendor's installer checks its own download: HTTPS from the vendor, then the SHA-256 in the vendor's manifest. It then runs the binary it downloaded, to finish setting up, before Oriel regains control, as it does for anyone who runs it. Oriel's own check comes before Oriel first runs the binary, and again whenever the file changes: `/usr/bin/codesign` verifies it, `/usr/sbin/spctl` says it is notarized, and its Team ID is Anthropic PBC's, `Q6L2SF6YDW`. Oriel never runs a binary that fails, and its row says so.
  - **Sign in:** `claude auth login --claudeai`, with stdin closed. The CLI opens the vendor's page in the default browser itself, and the browser hands the sign-in back to the CLI's own listener on localhost. The CLI stores the credential where it always does. Oriel waits for the process to end, brings its window to the front, and checks again.
  - **Update,** for a version too old for the harness (0037): `claude update`. A Homebrew or npm install is the person's own: Oriel names its command and doesn't run it. A version too new, such as Claude Code 3.0, which 0037 refuses, gets no Update: its row says Oriel's next update will support it, and offers an API key.
  - **Cancel** and **Start again** stop the child's process group; Start again then runs it afresh. Quitting Oriel stops them too.
- **Oriel never handles the sign-in.** It never reads the CLI's files or credential store, never writes to the CLI's stdin, and never takes a code to paste. It never opens the link the CLI prints, because that one ends on a page with a code to paste. If the browser can't hand the sign-in back, the way out is the CLI's own sign-in in Terminal, written out step by step, or an API key.
- **How Oriel knows.**
  - Installed: the binary is found as 0036 says, and in `~/.local/bin`, where its installer puts it.
  - Signed in: the CLI's own answer, through the harness's start check (0037).
  - The plan and the account's email: `claude auth status --json`. They are shown in the row while the setup or Settings is open, and never stored, logged or sent.
  - Works: one test turn when the person clicks Continue, through the harness's title path on its smallest model. It is the only check that proves the plan answers. While it runs, the button says "Checking that Claude Code answers…". If it fails, the row says why in one sentence: a usage limit, with when it resets and Continue anyway; no connection, with Try again; a plan without access, the no-plan state; or a configuration the harness refuses, with the harness's sentence and Show details. Each also offers an API key and Set up later.
- **The row.** Claude Code is one row, the same in the setup and in Settings (OA-181): its name, the plan it uses and its maker; its state; once signed in, the plan and the account's email; and one action. The states take the harness's names where it has them:
  - checking;
  - `missing`: Install, with its size;
  - installing: the phase, the time so far, and Cancel;
  - `unsupported`: Update;
  - `signed-out`: Sign in, which opens the vendor's page;
  - signing in: "A tab opened on claude.ai. It asks you to let Claude Code use your Claude account", with Start again and Cancel;
  - no plan: signed in on a plan that can't run it, with See plans and Use another account;
  - failed: Try again, Show details, and Other ways;
  - ready: picked.
- **Codex** can't run Oriel yet (0040). Oriel only checks whether its file is there; it never runs it, installs it, or points anyone at its sign-in. Found, it gets a row with no action, in 0040's words: "Oriel can't run on Codex yet, because Codex can't be limited to Oriel's one tool. Install Claude Code and sign in to it, or add an API key." The row is never a choice. Its path opens once a Codex release meets 0040's three conditions: only Oriel's tool, no user configuration on the person's own sign-in, and a report of the tools the model sees. Then it gets Claude Code's row, states and commands, with `https://chatgpt.com/codex/install.sh`, `codex login` and OpenAI's Team ID `2DC432GLL2` (see Why).
- **A ChatGPT subscriber with no Claude plan** is told so plainly, and shown the shortest way in: an Anthropic API key, with nothing to install and about five minutes on Anthropic's site. A Claude plan and Claude Code is the other. With Codex found, its row says why; with nothing found, a line under the rows does: "Only have ChatGPT? Oriel can't run on it yet."
- **Choosing.** A ready Claude Code is picked, and an API key is the other choice, which the person can switch to in Settings. The happy path is one click: Continue with Claude Code. Use another account runs the CLI's sign-in again, after saying the CLI then uses that account everywhere on the Mac, and to sign out in the browser tab if it shows the old one.
- **No plan.** A Claude account on the free plan is told in its row that its plan doesn't include Claude Code, with See Claude plans and Use another account. Any other refusal shows the CLI's own sentence, with Show details.
- **An API key** is the way in without a plan: "Pay Anthropic per question instead" under the rows, then one field, "API key", with a link to Anthropic's console and a line saying Anthropic bills each question and the person can set a monthly limit there. One small request checks the key before it goes into the keychain (0036).
- **The first source** comes second: Jira, Slack or a folder. One is enough, and the step can be skipped. It says Oriel keeps the work on the Mac, and that only what a question needs goes to the AI, under the person's plan.
  - **Jira** asks for three things: its address, the email the person signs in with, and an API token, with three numbered lines for making one on Atlassian's page, its expiry included. That label is the setup's one "token". Any Jira Cloud site is accepted: `https://` and one name under `atlassian.net`, checked before credentials go anywhere. The person then picks the project from the list Jira returns, so nobody types a project key. A refusal names the fields and keeps the steps on screen (OA-125).
  - **A folder** comes from the system's folder picker, through the shell. Oriel only reads it, so with a folder alone the first run ends at the first answer: a change set needs Jira or Slack, and the overview's connect card says so.
  - **Slack** opens Slack's own approval page in the browser, then the person ticks channels. It waits for a story that makes Oriel's Slack app installable by anyone; until then the setup offers Jira and a folder.
- **The first sync** shows each source's progress, issues read of the total Jira reports and files read, then opens the overview as soon as one source is read. A source that fails says why in its row, with Try again and Change; one that reads nothing says so, such as a project with no issues or a folder with no notes. A one-time line there says what the window and a workstream are. On the first run, the top candidate's question to start from (0030) is an instruction, "Make … a workstream", so what the agent does matches what was asked, and the answer says the workstream is Oriel's and nothing changed in the source. As 0030 has it, the candidate's name shows only on the button: the message stays fixed wording with the row's ID, never a name or title, which may be synced text.
- **Skip, quit, come back.** Each step has Set up later or Skip for now. The setup stores its own progress: each step done or skipped, and when it finished. The AI chosen is a setting, the one Settings shows. Everything else is read fresh each time: the CLIs' states and the connected sources. Reopened before it finished, it opens at the first step neither done nor skipped. A child ends with the server, so a half-done install or sign-in shows its row's state again. Once finished, the setup never shows again. With no AI, the ask bar says so and opens Settings; with no source, the overview's connect card does.
- **No sample world.** The first run starts on the person's own work.
- **The budget** (SPEC §4): the clock starts at the setup's first screen on a fresh data folder and stops at the first approved change set, through Jira. Three paths, each timed: ready (installed and signed in), under five minutes; sign-in only, which may add one; install and sign-in, which may add three. "Token" appears at most once. Telemetry (SPEC §7) measures people on each path, with each phase's time, Atlassian's page included. OA-191's scripted run measures Oriel's part, with credentials prepared. The walkthroughs' guesses miss the budget by Jira's token, so that is the step to shorten next (Rejected: signing in with Atlassian).
- **Windows,** where it differs: the installer is `install.ps1`, run by PowerShell; Claude Code lands in `%USERPROFILE%\.local\bin`; a GUI app gets the user's PATH with no login shell; the signature check is Authenticode, for the same vendor. Sign-in is the same.

**Why.**

- **What the CLIs do (OA-190),** Codex's included for when it opens. Measured on the maintainer's Mac with `claude` 2.1.314 and `codex` 0.166.0, through their help, their installer scripts (read, not run), their status commands, a throwaway home for the signed-out cases, and their vendors' docs:
  - Neither installer asks anything without a terminal. Claude's never asks; Codex's asks two yes-or-no questions only with a terminal attached, and `CODEX_NON_INTERACTIVE` answers no. Both install into `~/.local/bin` without sudo, check the download's SHA-256 against the vendor's manifest, and leave a binary signed with the vendor's Developer ID and notarized. Claude's leaves the shell profile alone; Codex's adds `~/.local/bin` to `~/.zprofile`, as it does for anyone.
  - The downloads: Claude Code is 313 MB, or 108 MB where `zstd` is installed, which stock macOS isn't; Codex is 166 MB. Anthropic's docs: "The install command shows no progress while it downloads."
  - Sign-in needs no terminal. With stdin closed, `claude auth login` prints three lines and waits for the browser, which it opens itself (checked in a throwaway configuration, with the browser opener stubbed). `codex login` waits on `localhost:1455`.
  - Status is local and fast: `claude auth status --json` in 0.15 s, with the plan; `codex login status` in 0.05 s, and app-server's `account/read` in 0.4 s, with the plan. Each says when it is signed out. None proves the plan answers.
  - A test turn on Claude Code's smallest model took 1.5 s: about 2,900 input tokens, mostly cached, and 4 out. Codex took 8.9 s, with 14,700 input tokens (12,300 cached). Signed out, Claude Code fails in 1.8 s; Codex retries for over 10 s, so status comes first.
  - Plans. Anthropic: "Claude Code requires a Pro, Max, Ultra, Team, Enterprise, or Console account. The free claude.ai plan does not include Claude Code access." OpenAI: "ChatGPT Work and Codex are included in your ChatGPT Free, Go, Plus, Pro, Business, Edu, or Enterprise plan".
  - The Claude desktop app keeps its own copy of Claude Code in its own folder, which it updates and prunes. It installs nothing for other apps, so most Claude subscribers start at `missing`.
- **No terminal, with a log,** over plain steps alone and over a guided terminal. Every interactive moment the CLIs have is covered without one: neither installer asks, and both sign-ins open the browser themselves. A failure needs a sentence the person can act on and a log someone else can read, which costs one disclosure. A terminal pane needs a pty, which means a native module with install scripts (0008), and a terminal renderer, another dependency or our own. It accepts any keystroke, so its allowlist would be a promise in the page, and it is the thing the person must not meet. An Electron shell changes none of this.
- **Two walkthroughs** of the prototype, one a Claude Pro subscriber and one a nervous ChatGPT Plus subscriber, each given only a persona and the screenshots, guessed about 11 minutes from the first screen to an approved change. Four of those minutes went on Jira's token, not on the AI. Both would stop at Terminal. Round 2 answered what they raised: plans before product names, what installs and where the work goes, an install that shows it is moving, a refusal that keeps its help, and a first answer that says what changed and where. The table is in the pull request. The ChatGPT subscriber walked a Codex path that 0040 has since closed; their route now is an API key, which no walkthrough has tried yet.
- **A shipped desktop app that drives these same CLIs** checks each one and offers Install or Sign in per row, then opens a terminal under the row with the command typed in, for the person to press Enter. That suits developers. Followed: one row per CLI with the same states in the same order, the vendors' own installers and sign-in commands, version and status checks with time limits, and the plan and account shown once ready. Departed: no terminal pane, no code pasted through Oriel, and no install managed by Oriel with its own sign-in, which would hold a token Oriel keeps.
- **The vendors' terms,** quoted, not interpreted:
  - Anthropic, Claude Code's legal and compliance page: "Developers building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication through Claude Console or a supported cloud provider. Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow." Also: "Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription"; "Claude Code must be installed and run as published by Anthropic"; and "Advertised usage limits for Pro, Max, and Ultra plans assume ordinary, individual usage of Claude Code and the Agent SDK."
  - Anthropic, the Agent SDK overview: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK."
  - OpenAI, Codex's authentication docs: "Use API key authentication for programmatic Codex CLI workflows, such as CI/CD jobs." OpenAI also offers apps a route of their own, Sign in with ChatGPT: "Let users sign in with ChatGPT and use their ChatGPT plan for eligible AI requests in your app." It needs a client ID from OpenAI, and the app holds the person's token.
  - So the setup keeps to the plainest reading of those words: the vendor's unmodified binary, installed by the vendor's installer; sign-in only in the vendor's own page, completed by the CLI; nothing of the sign-in passing through Oriel; and an API key one link away. Whether Oriel driving the person's CLI on their plan is within those terms is a question for the vendors, which the maintainer asks before pilots.
- **No sample world.** It can't skip the AI step: answering needs a model, and a scripted stand-in would be the untrustworthy demo SPEC §1 warns about. Workstreams made in it wouldn't carry over to the person's own work. The fixture world is messy on purpose, with an injection story and a 10,000-character description, and a tidy one would be a second fixture to keep. A folder already gives a first source with nothing to sign in to.
- **The AI first.** It is the riskiest step and the slowest, so a blocker shows before the person types anything for Jira. For a subscriber it is also the familiar sign-in.

**Rejected.**

- **A guided terminal pane,** and a terminal with the command typed in. See Why.
- **A field for the code the vendor's page shows** when the browser can't hand back. It would pass a sign-in code through Oriel, which Anthropic's words rule out.
- **Oriel downloading the binary itself,** with a real progress bar. It would rewrite the vendor's installer, which Anthropic asks be the vendor's.
- **Homebrew or npm.** They assume developer tools the person doesn't have.
- **Driving the Claude desktop app's own copy.** It belongs to that app, which updates and deletes it.
- **Oriel's own sign-in for each CLI,** in a configuration folder of its own. Someone already signed in would sign in again, and 0036 drives the CLI signed in however the person signed it in.
- **Sign in with ChatGPT for apps, now.** It needs a client ID from OpenAI, and Oriel would hold a ChatGPT token, which 0020 rules out. It is the route to weigh if a ChatGPT plan should run Oriel before Codex meets 0040's conditions.
- **Signing in with Atlassian in the browser, now.** It would remove the walkthroughs' slowest step, but it needs an Atlassian app and somewhere to keep that app's secret. The `Credential` seam (SPEC §7) is for it.
- **A sample world.** See Why.

- 0037 is amended: the harness itself still offers no sign-in, but the first run starts the CLI's own, which Oriel never sees.
- SPEC §4 restates the budget; §5 says Oriel may start the CLI's sign-in but never sees it; §7 gains the setup's telemetry and a model-access line that matches 0036, 0037 and 0040.
